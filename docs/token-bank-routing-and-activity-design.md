## 分组由管理员配置，C 端只授权账号

C 端不提供分组选择。添加页显示平台、账号授权方式，以及只读的接收分组、分成比例；后台按平台匹配管理员已经配置的接收分组。已有账号创建、授权、导入、编辑服务继续复用。

改造前，多个同平台接收组会全部绑定。本次改为：原渠道接收配置 → 筛选启用、已关联且平台相同的组 → GPT 再核对上游真实套餐 → 按接收优先级只取一组 → 创建原 accounts 记录并绑定当前用户。C 端传入的 group_ids 仍由服务端覆盖，编辑不能自行更换分组；更换 GPT 授权时重新核验、重新选择单组。

配置变更影响之后的添加；已有账号不会因此自动迁移，应由管理员在原账号管理中批量调整。一个账号可以绑定多个分组，按实际请求所属分组、渠道计费及分账。

## 月卡分账口径

当前结算基数为 BalanceCost + SubscriptionCost。月卡调用按额度消耗金额参与分账，并非按月卡购买款实时摊分。月卡售价、赠送额度及使用率会影响平台实际收益；绑定月卡前需确认接受该既有口径，不在本方案内另建摊销或结算系统。

## 收益展示：顶部一行广播与排行榜

用户确认：Token 银行顶部使用一行滚动广播，附“收益榜”入口，点击用原弹窗展示累计到账收益前 10 名。不使用默认收起的储蓄动态，不增加个人公开开关，不提供提现。后台原系统设置增加总展示开关，默认关闭；有真实数据后管理员可以开启。

数据直接读取原 account_revenue_ledger 已提交的 owner_amount，与站内余额入账保持同一口径。排行榜按同一用户多个账号合计，广播取近期真实到账。服务端脱敏用户名，不输出用户 ID、完整姓名、邮箱、账号凭据、余额、消费者资料。无收益时显示空态，不生成模拟播报。金额复用现有 USD 站内计价单位，不换汇，也不冒充可提现现金。

广播每 60 秒更新数据，页面隐藏或卸载后停止刷新；总开关关闭时接口不返回榜单和广播明细。使用现有卡片、图标、按钮、弹窗和暗色样式，不另造页面体系。

## GPT 套餐准入与接收优先级（用户已确认实施）

用户明确：只有一个默认接收组；匹配多个组时，只加入管理员设置的接收优先级最高的一组。此前“加入所有匹配组”的建议撤回。优先级代表平台运营排序，不把瞬时调用量或不同模型单价直接当作账号收益排名。

平台相同只完成第一层检查。GPT Free、Plus、Pro 各档不能只凭名称或用户填写的 plan_type 匹配。后端必须复用原 OAuth 交换、上游刷新和套餐查询取得可信套餐，再筛选满足平台、账号类型、套餐条件的接收组。现有 GPT Pro ×20 接收组仅允许 Pro 20x；Pro 5x、Plus、Free、Business 不混入。核验不能区分时拒绝进入该组。

创建、JSON 导入、重新授权都要经过同一校验；账号套餐降级或更换授权后，还要重新检查现有分组准入。未知套餐不进入要求 Pro 的组；没有合格接收组时明确提示暂未开放对应套餐，不落到高价组。管理员维护原渠道配置与分组，C 端只看到识别出的套餐和只读接收结果。

核验边界：C 端传入的 plan_type 和 JWT 解码内容不能证明套餐。本次使用服务端固定上游查询或实际刷新返回值建立可信标记；无刷新凭据的旧最佳努力 enrichment 不作为准入证据。线上 GPT 储蓄接收已开放，仅允许经上游核验的 Pro20x。

## 验收边界

- 当前平台隔离仍保持；后续新增套餐校验通过后，只选择优先级最高的一个合格接收组。
- 未开放平台在授权前提示；原管理员账号管理仍能按已有权限配置多分组。
- 原有账号迁移明确列出受影响账号，不把接收配置保存当作迁移完成。
- 月卡按既有额度口径分账，重复请求不重复入账；成本和售价不因收益展示变化。
- 广播及榜单只取真实成功账本；服务端脱敏；总开关关闭不返回明细；页面不可见后停止刷新。


### 本次实施契约

- 扩展原渠道 token_savings.receiving_rules，每条包含 group_id、priority、allowed_plans，保留原 receiving_group_ids。priority 范围 0–1000，数值越高越优先；相同优先级按 group_id 从小到大确定一组。
- OpenAI 接收组必须显式指定允许套餐，不能从组名推导；无套餐规则的历史 OpenAI 接收配置不自动放行。非 OpenAI 原有配置兼容。
- 服务端使用原上游 HTTP 客户端核验 access token 的套餐，PAT 复用 whoami；仅有 refresh token 时复用原刷新接口，并保存更新后的凭据。客户端的 plan_type、JWT 解码结果和自称的验证标记不作为准入证据。
- 只为 owner_user_id 非空的储蓄账号施加新限制；创建、导入和换凭据走同一资格校验。旧授权换成低档账号后必须重新匹配合格接收组。
- 调度前检查该组允许套餐、服务端验证标记及当前上游套餐状态；上游刷新确认降级或缺少可信套餐时，旧验证不得继续放行。影子账号按所属主账号核验。
- 不重新计算 Token 价格，不改变既有扣费和 80/20 分账，不将售价 0.8 倍等同于用户分成 80%。原“30% 毛利”仍不能解释为分账后平台占比达到 30%。

### 套餐变化的检测边界

添加、导入、换授权均向上游核验。凭据刷新、上游返回套餐变化后，下一次准入及 WebSocket 后续轮次读取新状态；已观测到的降级或核验失败不能沿用旧 Pro 标记。仅 access token/PAT 且上游尚未报告变化时，本版不新增定时套餐查询，不能承诺在上游静默变更套餐的一刻同步发现。测试覆盖模拟上游响应和真实本地 PostgreSQL，尚无真实 Pro20x 用户授权成功的端到端证据。
